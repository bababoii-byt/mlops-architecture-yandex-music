
# Архитектура ML-системы формирования семейного плейлиста Яндекс Музыки

## 1. Описание проекта

Проект представляет собой реконструкцию архитектуры ML-системы для формирования семейного музыкального плейлиста на основе предпочтений участников семейной подписки Яндекс Плюс.

Рассматривается процесс регулярного обновления плейлиста, в котором объединяются музыкальные предпочтения нескольких участников, рекомендации на основе похожих пользователей и редакционные подборки.

Это проектирование предполагаемой архитектуры, а не описание реальной внутренней реализации Яндекса.

## 2. Бизнес-процесс

**Компания:** Яндекс  
**Продукт:** Яндекс Музыка  
**Процесс:** Формирование и обновление семейного музыкального плейлиста.

Цель процесса — сформировать музыкальную подборку, которая учитывает общие и индивидуальные предпочтения участников семьи.

Результат — опубликованный семейный плейлист, доступный участникам подписки.

## 3. Границы системы

В рамках проекта рассматривается только процесс формирования семейного плейлиста.

В систему входят:
- запуск регулярного обновления;
- получение состава семьи и настроек участия;
- сбор музыкальных кандидатов;
- подготовка признаков;
- ML-оценка треков;
- формирование и публикация плейлиста;
- сбор обратной связи.

Внешними по отношению к проектируемой системе считаются пользователи, сервис управления семейной подпиской, источники истории прослушиваний, рекомендации похожих пользователей и редакционные подборки.

## 4. Предполагаемая логика формирования

Для проектирования приняты следующие допущения:

- Семья может включать до 5 участников.
- Плейлист обновляется раз в неделю.
- Целевой размер плейлиста — 50 треков.
- Каждый участник отдельно разрешает или запрещает использование своих предпочтений.
- Для персонализированного формирования необходимо не менее двух согласившихся участников.
- История отказавшихся участников не используется ни для формирования кандидатов, ни для их оценки.
- Кандидаты поступают из историй прослушивания согласившихся участников, рекомендаций похожих пользователей и редакционных подборок.
- ML-модель оценивает пригодность треков для семейной группы.
- Итоговый список формируется с учётом общих и индивидуальных интересов, без дублирования треков.
- Если ML-модель недоступна или её результат не проходит проверку, используется резервный алгоритм.
- Если сформировать полный плейлист невозможно, сохраняется предыдущая версия.

Распределение треков по категориям и пороговые значения ML-модели являются проектными решениями.

## 5. ML-компонент

ML Inference Service получает подготовленные признаки кандидатов и оценивает, насколько каждый трек подходит семейной группе.

Основные компоненты:
- Feature Preprocessor — проверяет и преобразует признаки.
- Model Resolver — выбирает версию модели.
- Model Inference — рассчитывает оценки треков.
- Score Validator — проверяет корректность результатов.

Версии моделей хранятся в Model Registry.

## 6. Обратная связь и оценка качества

После публикации плейлиста система собирает пользовательские события:
- лайки;
- пропуски треков;
- добавления в избранное;
- прослушивания.

Эти события используются как неявная обратная связь для оценки качества рекомендаций и подготовки следующих версий модели.

Лайк рассматривается как положительный сигнал, пропуск — как потенциально отрицательный, а длительное прослушивание — как дополнительный сигнал интереса. Эти события не являются гарантированной оценкой того, понравилась ли песня пользователю.

## 7. Архитектурные решения и допущения

Внутреннее устройство реальной системы Яндекса публично не раскрывается в рамках использованных источников. Поэтому состав сервисов, технологии, схема хранения данных, алгоритм формирования плейлиста и ML-процесс являются самостоятельно разработанными архитектурными решениями.

Предполагаемый технологический стек:
- Python, FastAPI — сервисы обработки и ML-inference;
- PostgreSQL — хранение плейлистов;
- Apache Kafka — передача событий обратной связи;
- MLflow — реестр моделей;
- Airflow — запуск регулярного процесса.

Указанные технологии выбраны для проектируемой архитектуры и не являются утверждением о стеке Яндекса.
